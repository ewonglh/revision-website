# Proposed portable contracts and recovery

Status: research proposal for #30, not implemented interfaces or accepted backend decisions. JSON over HTTPS; opaque identifiers; UTC RFC3339 timestamps plus display timezone; integer marks in declared units; explicit schema versions. Do not introduce these objects into the frontend until a reviewed implementation child needs them.

## Data boundaries

| Record                 | Required fields / invariant                                                                                                                                                                                                                  |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Principal / grant      | Verified server subject, owner, offering, capability, grant version/revocation; never trust a browser-supplied owner ID                                                                                                                      |
| Source revision        | ID, owner, offering, content hash, media type, original private object reference, provenance/permission, supersedes, extraction version/state, source precedence, retention state                                                            |
| Evidence block / asset | ID, source revision, physical page index and printed label, bounding box/coordinate system, section/text span, excerpt hash, asset reference, review state, visibility/release policy; a single PDF can contain differently protected blocks |
| Question version       | Immutable prompt/parts/shared assets, part IDs/dependencies/marks, question family, prompt-source anchors, rubric/key version, solution-source anchors kept separate, author/reviewer provenance                                             |
| Rubric version         | Criteria, maximum marks, accepted alternatives, explicit dependencies/follow-through/caps, trusted/reviewed/proposed status and reviewer; no AI-proposed key becomes official                                                                |
| Attempt / draft        | Owner, offering, pinned question/profile versions, part drafts, revision counter/ETag, assistance/exposure, mode, authoritative start/deadline/release timestamps, status                                                                    |
| Submission             | Immutable original answer/media hash and submitted part states (blank/skipped/answered), draft revision, server receivedAt, captured question/rubric/profile versions, idempotency key                                                       |
| Marking result         | Submission ID/hash, result version, criteria (earned or null, possible, status/reason), cited blocks/revisions, rubric/model/prompt/retrieval/checker versions, evidence limitations, dispute/override/effective-result references           |
| Check evidence         | Type: key/deterministic/executed/AI-review/formal; actual tool/version, input hash, scope and outcome/artifact hash. `not_run` and `unsupported` are explicit; no fabricated execution                                                       |
| Durable job            | Owner/offering, input version hashes, unique operation key, state/checkpoint, lease/fencing token, attempt counts, limits, budget reservation, provider request ID, output references and error class                                        |
| Learning event         | Unique effective-result/criterion version, skill, independence/exposure, timestamp; replacing an effective grade retracts/recalculates evidence without treating regrading as a new attempt                                                  |

Question, solution and learner permissions are independent. Marking-only access to a reserved solution never authorises returning it to a learner. Material revocation must invalidate derived blocks, search entries, source previews and cached results. Old attempts preserve permissible provenance; evidence can become unavailable, visibly, rather than bypassing deletion. Retention/deletion of shared and historical content is unresolved before invited use.

## Initial API surface

Every mutation authenticates, authorises current ownership/grants, validates bounded input and returns a request ID. Unauthorised object access gives a non-disclosing not-found response. Public client responses exclude provider prompts, private object keys and hidden solutions.

| Operation                            | Request / response and failure semantics                                                                                                                                                                                                                                  |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /v1/imports`                   | Owner-authorised offering, short-lived upload reference, declared hash/type/size and source metadata; idempotency key -> `202 {importId, jobId, statusUrl}`. Validate hash/MIME/limits and quarantine before extraction; URL ingestion is not arbitrary server-side fetch |
| `GET /v1/jobs/{id}`                  | `{state, stage, retryable, nextAction}` from durable record; safe error code, no raw provider logs. Includes queued/running/needs-review/paused-budget/succeeded/failed/cancelled                                                                                         |
| `POST /v1/jobs/{id}/cancel`          | Idempotent cancellation request; check before next paid step. A paid call already sent may still charge; store its completion privately without publishing cancelled output                                                                                               |
| `POST /v1/imports/{id}/publish`      | Reviewed draft revision + `If-Match`; publish immutable question/source versions after semantic/permission gates. `409` for conflicting revision; partial failures retain unreviewed material                                                                             |
| `PUT /v1/attempts/{id}/draft`        | Part content, client revision and `If-Match`; returns new ETag and savedAt. Conflict returns recoverable conflict metadata; preserve both versions locally/server-side for explicit resolution                                                                            |
| `POST /v1/attempts/{id}/submit`      | Frozen answer hash/revision and idempotency key; transaction pins original, seals eligible attempt and inserts outbox/job once -> `202`. Same key+payload returns same submission; same key+different payload -> `409`                                                    |
| `GET /v1/submissions/{id}/results`   | Versioned visible criteria/results, pending states and check coverage. Release policy applied on each read; withheld results do not leak through counts, errors or snippets                                                                                               |
| `POST /v1/submissions/{id}/regrades` | Explicit rubric/policy version and reason -> new bounded job/result; original submission remains immutable; caller needs authority and budget                                                                                                                             |
| `GET /v1/evidence/{blockId}`         | Reauthorise owner/offering/revision/release at fetch; return allowed excerpt/crop only. Never give a whole original PDF signed URL if it contains reserved solution pages                                                                                                 |

Marking-only retrieval is a private service operation, not an unscoped browser search endpoint. Its input pins principal/grant version, offering, question/rubric/source revisions, intent and purpose. Apply visibility filters before search and reauthorise blocks before assembly. Record returned anchor IDs and reasons for absent/conflicting evidence. Cache keys include ownership/grant/release/revision and purpose; revocation invalidates them. Document instructions cannot change tool permissions or scoring policy.

## Deadlines and concurrent saves

At exam start, a database transaction snapshots the confirmed profile and server `startedAt`, persists `deadlineAt = startedAt + allowedDuration`, and returns it. The browser displays remaining time; it cannot extend the deadline. Accommodations create an authorised versioned adjustment with an audit reason. An alarm/worker may seal promptly, but every save and submit enforces deadline and state transactionally even if the alarm is delayed.

Proposed initial policy: only server-received, durably acknowledged draft revisions received before `deadlineAt` are eligible; no implicit grace for offline/client timestamps. A due attempt seals the latest eligible revision exactly once. Refreshing cannot restart it. Late/offline work stays recoverable as a separately labelled practice copy and cannot silently change the exam score. This policy needs review with the actual exam profile before implementation; high-stakes certification is out of scope.

Use a single transactional authority for deadline, draft revision and sealing. Test save-vs-submit, deadline-vs-submit, two tabs, retry after lost response and refresh after expiry. A Durable Object may coordinate an attempt, but choose an authority explicitly; do not let a DO clock and a separate DB both accept competing submissions. D1 conditional batches or Postgres transactions require implementation-specific proof via concurrency tests, not a diagram alone.

## Bounded work and failure recovery

Proposed per-job limits: 20 pages/20 MB per extraction batch, 10,000 input and 3,000 billed output tokens per ordinary marking call, one submission version per job, two concurrent expensive jobs per owner, configurable project limits. Large imports split into bounded batches with a persisted manifest. The cost worksheet uses expected 8k/2k ordinary and 16k/4k escalation counts; escalation has a separate hard 20k/6k envelope. Final limits require actual page and model measurements. Provider-specific reasoning tokens must fit the billed-output cap.

Use no more than two primary sends total (one initial plus one retry, covering transient transport/429/5xx or a single schema-repair attempt), then at most one distinct escalation call on unresolved criteria if budget permits. Total ceiling: three billable sends. Delays: bounded exponential backoff/jitter, honour Retry-After within a 15-minute job window. Never retry authentication/permission failures or unreadable input automatically. Uncertainty or conflicting sources goes to review rather than repeatedly requesting a different grade. Use one schema validator; model-generated JSON is untrusted.

Transport timeouts can leave billing uncertain. Persist request IDs and call intent before sending; reconcile status where supported. Without a provider idempotency/status guarantee, mark the call `unknown` and require explicit retry within the same attempt/budget ceiling. Do not automatically repeat a possibly billed call merely because the queue redelivered a message.

| Failure                                        | Recovery invariant / future behavioural check                                                                                                                            |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| DB commit succeeds; dispatch fails             | Commit outbox row with submission; dispatcher reconciles unsent rows, deduplicates by operation key; no lost saved answer                                                |
| Duplicate/out-of-order queue delivery          | Queue delivery is at least once [S06]; unique job/result keys, leases/fencing and compare-and-set checkpoint prevent duplicate effective results                         |
| Worker dies mid-import                         | Retry only unfinished page/checkpoint; keep original and reviewed repairs; never publish half-repaired question as ready                                                 |
| Model returns malformed/unsupported grade      | Validate criteria, ranges and known citation IDs; bounded repair or review. A valid schema alone does not validate reasoning                                             |
| Citations/support are missing or contradictory | Affected criteria remain unresolved/provisional; record source conflict; never manufacture quotes or a confident zero                                                    |
| Permission/release changes during a job        | Reauthorise at evidence assembly, result commit and user read; discard disallowed outputs and purge stale retrieval/caches                                               |
| Monthly budget exhausted                       | Atomically reserve worst-case billable envelopes before sends, reconcile actual usage, pause new paid work at cap; drafts, exports and existing results remain available |
| Cancel/deletion races with completion          | Tombstone/cancel generation checked at commit; do not resurrect content or publish delayed outputs. Purge original/derived/index/cache/provider files per policy         |
| Regrade or manual override                     | Append labelled result; replace effective learning event idempotently; self-assessed overrides do not become calibration gold                                            |

Usage reservations must cover in-flight work and retries/escalation, not just provider totals reported later. Queues carry opaque references, not course text. Keep raw outputs in restricted short-lived diagnostics if permitted, with no content in normal logs. Budget stops are owner-configured; the scenarios do not invent the owner's cap. Before production, choose retention durations, provider data terms, backup/restore policy and invited-sharing deletion rules.

These failure scenarios specify meaningful tests for future slices. None has run against infrastructure in this research PR.
